# phonton-cli v0.27.0 — Local Rust checks run cargo

0.27.0 fixes bugs and waste in local goals, measured in a re-run of the
51-exercise Aider Polyglot slice on 0.26.0 with `qwen3.5:4b`. It changes no
tuned defaults: thinking mode stays as calibrated and runs start at
temperature 0. Only a run whose model repeats itself switches to sampling
(below).

## Rust checks run cargo

Where `cargo.exe` is a symlink to `rustup.exe` (scoop's `rustup-msvc`
installs it that way), every local Rust check failed before cargo started:
Phonton resolved the link and started rustup, which dispatches on the name it
was started as and rejected `test` as a subcommand. All 51 local Rust
Polyglot runs on the benchmark laptop (0.25.0 and two 0.26.0 runs) failed
this way.

The check now runs the proxy under its own name. Its directory is still
resolved, and both the path and the link target must be outside the
candidate directory.

With cargo running, the next failure showed up: Polyglot's Rust exercises
ship without a `Cargo.lock`, `cargo test` writes one, and Phonton stopped the
run at its baseline check because the check had added a file. A
`Cargo.lock` beside a captured `Cargo.toml` is now ignored, like `target/`.
Anywhere else, an added file still stops the run.

## Fewer wasted attempts

In the 0.26.0 re-run, 65 of 142 local candidates never reached the tests:
30 at the goal-name gate, 24 that changed nothing, 10 that hit the output
limit and 1 repeated candidate. The 22 repeated replies below overlap those
counts.

- **Repeated replies.** At temperature 0 the model often answered a new
  request with exactly the same reply (22 of 142 candidates). A reply that
  repeats an earlier one byte for byte, or a candidate identical to an
  earlier one, is now rejected without checks and the run asks again. From
  then on that run samples at temperature 0.7 with the candidate number as
  seed, recorded on each candidate as `sampling`. Runs that never repeat
  themselves keep temperature 0, and two repeats in a row still stop the
  search.
- **Search/replace that changes nothing** (24 of 142). When a reply leaves a
  file of at most 300 lines unchanged, the next attempt shows the whole file
  and asks for the complete corrected file, when the file and its rewrite
  fit the calibrated context and output reserve. When they do not fit, an
  ordinary edit runs from the same parent, and the receipt says so.
- **The goal-name gate.** A candidate that did not add an identifier the goal
  names was rejected before its checks (30 of 142). Across three local
  runs of the slice, 71 such candidates were rebuilt and tested and none passed, so with
  checks selected the gate is now a warning: the checks decide, and a candidate that passes them is
  review-ready with an advisory in the receipt and in the run summary.
  Review those: a weak test suite can pass an edit that changed the wrong
  thing. Without checks, without approval to run them on the host, or when
  the checks did not all run and pass, the gate still rejects.

## Longer goals

Local goals were refused above 8,192 bytes before a model was chosen; two
Polyglot exercises never ran. The limit now comes from the calibrated
context: three quarters of it, in bytes, because edit output takes at most a
quarter (12,288 bytes at 16,384 tokens). Whether the source also fits is
still checked when the prompt is assembled.

## Setup failure paths

A first run as a new user on the benchmark laptop found setup failures that
stopped without saying what to do next:

- `phonton models setup` downloaded a model that could never load and then
  failed calibration. On a 16 GB laptop with a 6 GB GPU, `qwen3.6:35b-a3b`
  meant 22.6 GB of weights for nothing. With the managed runtime, setup now
  checks before downloading that the weights, a 4K-token cache and the
  runtime fit in the largest GPU plus all of RAM. That model is refused with
  nothing downloaded, and the message names the setup command for a model
  that fits. An external runtime endpoint gets no such check.
- When the drive is too small for the runtime, setup now says to free space
  or choose a folder on another drive with `phonton models storage FOLDER`.
- A local goal with no model set up now says that nothing ran and names the
  setup command for the machine. In a folder that is not a Git repository it
  says why it stopped and suggests `git init`.
- A rerun of setup no longer claims the full model size is left to download:
  the figure is an upper bound, because layers already in the store are not
  downloaded again.

The `qwen3.5:9b` slice (see Model recommendation) found one more: a local
goal refused before it started for lack of free memory now says that nothing
ran and no file changed. When the model is too big for the free memory, it
also says to close other programs or choose a smaller model from
`phonton models catalog`.

Some of those refusals were Phonton's own arithmetic. On 20 Exercism Python
exercises with `qwen3.5:4b` (2026-11-10, same laptop, other programs open),
4 of 20 goals were refused before any model call. Ollama reports this model's
attention as one KV head count plus per-layer `recurrent_layers` flags;
Phonton multiplied the head count by all 32 layers when 8 keep a cache, so it
planned for 2 GiB of cache at 16,384 tokens instead of 512 MiB, sized the
model as a CPU offload and asked for RAM it did not need. Flagged layers are
now left out: the estimate is 4.9 GB, the model fits the 6 GB GPU, and a goal
needs 1.5 GiB of host RAM free.

## Model recommendation

`phonton models catalog` now recommends `qwen3.5:9b` from 10 GB of model
memory instead of 6 GB. A laptop with a 6 GB GPU and 16 GB of RAM counts as
8 GB and gets `qwen3.5:4b`, the model measured on that laptop; no measured
run there has beaten it. On the same 51-exercise slice and laptop, with other
programs holding memory, `qwen3.5:9b` calibrated only an 8,192-token context
because 16,384 tokens did not fit the free memory; `qwen3.5:4b` had calibrated
at 16,384. `qwen3.5:9b` passed none of the 16 Python exercises that ran,
where `qwen3.5:4b` passed 1 of 17. All 17 of its Rust runs and 13 of its 17
JavaScript runs were refused for lack of free memory, and one Python and one
JavaScript goal were too long for its context. Of the 3 JavaScript runs, only
`ledger` passed, and `ledger` passes with no edit. The help and the Ollama
provider default use `qwen3.5:4b` too.

## CI and release

- CI runs clippy and the workspace tests on Windows, including the symlinked
  rustup-proxy case.
- `Publish npm` waits up to 20 minutes for npm to make a new version visible.
  It failed after the successful 0.25.2 and 0.26.0 publishes, when npm took
  5-7 minutes.

## Verified

- Regression tests cover the symlinked rustup proxy (and a symlink inside
  the candidate pointing out), repeated replies and seeded resampling, the
  whole-file retry and its limits, the gate with and without checks or host
  approval, the scope of a goal that names files by path, the
  context-based goal limit, and the generated `Cargo.lock`.
- One local Rust Polyglot exercise (`luhn-from`, `qwen3.5:4b`) on the
  laptop where every earlier local Rust run failed: cargo ran the tests for
  all four candidates. Three failed them and one hit its output limit, so
  the exercise still fails, but on its tests.

## Measured

The 51-exercise Aider Polyglot slice (17 exercises each in Python,
JavaScript and Rust) with `qwen3.5:4b`, run twice on 0.27.0 (commit
`571ebff`) on the same laptop: 3 passed in each run (Python 1, JavaScript 2,
Rust 0). One JavaScript pass, `ledger`, is a refactoring exercise whose
tests pass before any edit; Phonton changed nothing there. Each run marked 2
candidates ready for review, and both passed the exercise's tests. 0.26.0
also passed 3, so these fixes gained no pass on the slice. They remove
failures that came from Phonton rather than the model: every Rust check now
reaches cargo.

The fixes made after those runs (path scope, the goal-name gate when checks
cannot judge, setup messages) do not change this slice: it names its files
with `--files`, runs its checks on the host, and every candidate marked
ready passed all of its checks.

## Still limited

- When a file is too large to rewrite whole, the next attempt is an ordinary
  edit from the same parent instead of the search's own next choice, such as
  a restart.
- Prompts are budgeted at one byte per token, so the longest Polyglot goal
  (`beer-song`, 12,628 bytes) still does not fit a 16,384-token context.
- The whole-file retry needs an output reserve of about a third of the file's
  size in tokens; larger files keep search/replace.
